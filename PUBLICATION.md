# Publication and maintainer setup

This project is prepared for a **new public repository** named `rcarigna/medieval-dynasty-modding`. It has independent Git history and contains only publication-reviewed material. Do not copy another repository's Git metadata, logs, operational manifests, saves or extracted artifacts into it.

## Authorization and repository creation

Repository creation and Pages administration require authenticated GitHub permissions. Do not request or paste tokens into source files, workflow YAML, command-line arguments or chat. Use a supported GitHub authentication flow if the account owner approves it.

After authentication and the publication review, from this project's root:

```sh
gh repo create rcarigna/medieval-dynasty-modding --public --description "Unofficial evidence-based Medieval Dynasty modding reference" --source . --remote origin --push
```

If that name already exists, inspect its ownership, visibility and contents before setting a remote. Never force-push over unrelated content.

## GitHub Pages setup

1. In the new repository, open **Settings → Pages → Build and deployment → Source → GitHub Actions**. This requires Pages/administration rights.
2. Review **Settings → Environments → github-pages**, including any desired required-reviewer protection and allowed deployment branches.
3. Set repository Actions variable **PAGES_PUBLISH_ENABLED** to the exact string **true** only after reviewing the public content and approving publication.
4. Run the **Documentation** workflow on `main` (or push a reviewed change). Inspect both build and deploy jobs.
5. Confirm the deployed address reported by the deploy job. The configured target is `https://rcarigna.github.io/medieval-dynasty-modding/`; it is not a claim that deployment has completed.

The workflow runs build/validation on pull requests. Only trusted main-branch push/manual events in the named repository can upload/deploy, and only while the variable is true. Build permissions are contents:read; only the deployment job gets pages:write and id-token:write. No external credentials are embedded, and configure-pages is explicitly prevented from auto-enabling Pages.

A maintainer with existing appropriate authentication can set the variable and trigger the workflow with:

```sh
gh variable set PAGES_PUBLISH_ENABLED --body true --repo rcarigna/medieval-dynasty-modding
gh workflow run pages.yml --ref main --repo rcarigna/medieval-dynasty-modding
```

The setting must be enabled through the repository UI first. If permissions, organization policy or environment protection block deployment, stop at that gate; do not widen token scopes or change another repository's visibility implicitly.

## Before publication

Run source validation, the strict MkDocs build and generated-site validation. Review human-readable claims and licenses too. The checks reject common personal paths, credential patterns, unexpected binaries, unlisted pages and missing game-specific metadata; they cannot prove ownership or independently verify runtime observations.

The original example is **not runtime tested**. Building documentation does not execute it. No proprietary implementation, asset, third-party DLL or generated SDK is included.

## Maintenance

All prose lives under `docs/`; example source is under `examples/`. Keep Pages content generated by Actions, not committed build output. Update dependencies/action pins through reviewed changes and check Material's announced May 2027 support horizon. Future framework documentation should be added only for real, separately maintained versioned APIs.
